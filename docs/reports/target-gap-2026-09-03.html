1Fabric: что это и что нужно сделать

«Фабрика» в нашем окружении — это Fabric Agent Contract от passioncode-ai, закреплённый на версии 0.1.0, коммит 20a818e648a4c09a60df0126d11626922e8b9094. Проект-адаптер стоит плагином fabric-agent-adapter@0.3.1; сам контракт живёт в приватном репозитории, которого у нас на машине нет.

Fabric — это не транспорт и не ещё один MCP. Это контракт провайдера: стабильная идентичность (URI + ревизия + хеш содержимого), объявленные эффекты и класс данных, один профиль на способность, и — самое важное для нас — нормализованный конверт результата: атомарное done, разрешаемый proof, закреплённый scope, явный notVerified, неизменяемые артефакты.

Профиль — по способности, а не по проекту

Дерево решений скила даёт нам два разных профиля, и это разрешено:

СпособностьПрофильПочему именно он
query_database, get_schema, search_codebase, list_projects/connections MCP 2026-07-28 Ограниченные операции, планирование остаётся у вызывающего. У нас это уже нативно — app/mcp_server/, ASGI-монтирование на /mcp, принципал разрешается per-request через ContextVar.
«Спроси агента» — полный вопрос с планом, replan-ами, шагами, графиками A2A 1.0 Здесь жизненным циклом владеем мы: свой цикл, свой бюджет шагов, свои терминальные состояния (step_limit_reached, no_result), свои артефакты. Выдавать это за MCP-инструмент — соврать про владение задачей.
— local-runner Не наш случай: Fabric не запускает наш процесс.

Инспектор скила выдал recommendedProfile: mcp, но его доказательства — это файлы из .mypy_cache с «mcp» в имени. Эвристика по именам файлов; скил сам пишет, что код и документация её перебивают. Вывод верен, обоснование мусорное — я взял вывод из app/mcp_server/server.py, а не из его списка.

Готовность к биндингуNOT_VERIFIED Хоста/реестра Fabric 0.1.0 не существует. Никто это не пройдёт сегодня — и это не наша вина, а состояние контракта.

Что реально придётся построить

Конверта результата нет ни на одной поверхности

Fabric нормализует любой исход в done / proof / scope / notVerified. Мы отдаём прозу плюс необязательные таблицы и графики. Сырьё под это уже лежит и в этом хорошая новость: RequestTrace + TraceSpan — это proof; печати AnswerQualityGate и свежести — это notVerified; connection + project + индексированный SHA — это scope. Не хватает типизированного конверта, который это собирает. Это самая крупная работа во всём Fabric-треке и единственная, которая полезна нам независимо от Fabric — она же нужна для API, вебхуков и воспроизводимости отчётов.

Идентичности и эффектов не объявлено

Нужны стабильный URI провайдера, монотонная ревизия и неизменяемый хеш содержимого — то есть генератор манифеста на релизе, а не файл, который правят руками. Плюс класс эффекта на каждый инструмент: query_database идемпотентен, execute_raw_query защищён read-only-гардом но эффект не объявлен, а сбор аналитики мутирует — пишет в fact-таблицы. Сейчас всё три выглядят одинаково.

Что уже в нашу пользу

Нативный MCP с per-request принципалом; кросс-тенантный скоуп закрыт (#267); read-only принуждается на уровне СУБД, а не только регуляркой; типизированные частичные исходы уже существуют (step_limit_reached, no_result) — Fabric требует именно их сохранять при таймауте и отмене; трассировка уже персистится. Проект ближе к контракту, чем типичный HTTP-сервис.

2Цель против реализации — по способностям

2.1 Один агент над всеми источниками — сломано

В пайплайне нет ветки аналитики

app/agents/stage_executor.py:488-508 — match stage.tool знает шесть инструментов: query_database, search_codebase, analyze_results, process_data, query_mcp_source, analyze_git, synthesize. Ветки query_analytics_source нет — case _ вернул бы Unknown tool с категорией fatal.

app/agents/prompts/planner_prompt.py:30-68 — словарь планировщика тоже её не содержит, поэтому до fatal дело не доходит: планировщик просто никогда не знает, что аналитика существует, и строит план из БД и кода.

Почему это ровно та цель, которую вы описали. Path B выбирается по complexity=complex или needs_multiple_data_sources или estimated_queries≥3. Вопрос «сравни трафик из GA4 с регистрациями в базе» — это по определению needs_multiple_data_sources. Аналитика доступна только в одиночном tool-loop (Path A), то есть только в вопросах про одну аналитику. Продукт умеет «спроси GA4» и «спроси базу», но не «спроси и то и другое», и молчит об этом.

2.2 «Индексирует все связи» — только одна связь из шести

СвязьЕсть?Где
code ↔ DBда code_db_sync, точные состояния свежести, арифметика колонок; за последние недели вычищена от ложных таблиц
code ↔ codeда code_graph_symbols / code_graph_edges, IMPORTS теперь резолвится по суффиксу пути
DB ↔ DB (между подключениями)частично metric_relationships + reconciliation, но обе метрики обязаны быть DB-метриками
DB ↔ аналитиканет app/models/metric_definition.py:34-35 — у метрики есть source_table и source_column и нет source_type. Граф данных DB-образный по схеме: метрика GA4 в него не помещается, значит и связи с ней построить нельзя.
code ↔ аналитиканет
аналитика ↔ аналитиканет

Отдельно: единого индекса нет — четыре независимых хранилища (pgvector/Chroma для кода, BM25 для прозы, db_index для схем, ga4_* для аналитики) и никакого разрешения сущностей между ними. «Агент в любой момент найдёт любую информацию» сегодня означает «агент знает, в какое из четырёх хранилищ пойти» — и в пятое (аналитику) он не пойдёт вообще, если вопрос сложный.

2.3 Векторный поиск по репозиториям — работает, но лексическая нога пустая

Две критические поломки закрыты за последние дни и это надо сказать прямо: hybrid_min_score опущен до 0.0 с проверкой на буте, которая падает на значении выше потолка RRF (config.py:801-810, 1253-1258, #269), и номинальный isinstance, который опустошал RAG-ногу на продовом бэкенде, удалён (#274). Поиск перестал быть AND-гейтом.

Но остаётся то, из-за чего код всё ещё плохо находится по идентификатору: тела символов уходят только в векторное хранилище, а BM25-корпус собирается из LLM-прозы — строки 2.2 и 2.3 леджера. Запрос UserRepository::findByEmail лексической ноге не по чему совпасть.

Абстракция вендора чистая, хранилище — нет. Это и есть стена масштабирования

app/analytics/base.py — хороший контракт: каталог отчётов, один отчёт на один период, truncated/degraded рядом со строками. Добавить вендора на этом уровне дёшево.

app/services/analytics_collect_service.py:118-134 — FACT_TABLES_BY_SOURCE = {"ga4": GA4_FACT_TABLES}, и таблицы описаны руками, по одной на отчёт, с позиционным маппингом колонок. Плюс app/agents/tools/analytics_tools.py:55-62 — описание инструмента перечисляет пять отчётов GA4 буквально, одним глобальным определением на весь продукт.

Итог: вендор стоит адаптер + миграция + ORM-таблицы + правка описания инструмента. Три вендора — три миграции и три правки одного и того же текста. «Можно подумать о расширении на другие коннекторы» упирается сюда.

2.5 Отчёты и графики — есть

VizAgent, несколько графиков на один ответ, дашборды, публичный просмотр, расписания с алертами. Аналитический ответ рисует график (SCN-118). Эта часть цели закрыта.

Трек C — качество поиска, на котором продукт продаётся

Это строки 2.2, 2.3, 2.5, 2.10 леджера, и они относятся к цели напрямую: «векторный поиск по репозиториям, чтобы находить части кода».

  • C1 (=2.2, M) — тела символов в BM25-корпус. Сейчас там LLM-проза.
  • C2 (=2.3, S) — целые идентификаторы как термы BM25.
  • C3 (=2.5, L) — настоящий ретривер в CI-эвал. Сегодняшний гейт оценивает оракула, которому выдали ответы; поэтому ни одна из двух критических поломок поиска его не покраснила. Пока это так, любой регресс в поиске проходит CI.
  • C4 (=2.10, M) — префиксное совпадение при удалении: чанки символов не вычищаются.

Почему Fabric не первым. Контракт 0.1.0 не имеет реестра и рантайма — пройти допуск сегодня физически нельзя ни одному провайдеру. Готовый бандл — это готовность, а не подключение. Треки A и C двигают продукт, который вы описали; трек D двигает его совместимость с хостом, которого пока нет. Единственное исключение — D2: конверт результата нужен нам самим.

Шаги, которые может сделать только человек

  • Sentry — heroku labs:enable runtime-dyno-metadata: сейчас release в проде None, ни один трейс не называет коммит.
