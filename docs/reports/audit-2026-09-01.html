Механический скан: полезный выход — ноль

29 находок: 28 ложно-положительных и 1 ложно-отрицательная. All 28 'critical' findings were one pattern — a PEM header string. I checked four: a UI hint in the SSH manager telling the user what to copy, a fixture with four characters of base64, a placeholder with an ellipsis, and — most tellingly — a literal inside the security test that asserts a key never reaches a cache key. The history hits are the same test files plus ssh_tunnel.py and ssh_key_service.py, which legitimately contain the header for parsing. The one false negative: 'no error reporting found' while Sentry is wired and SENTRY_DSN is set in production.

critical retrieval verified by me S

Hybrid retrieval is an AND-gate: anything found by only one leg is always discarded

Evidence
config.py:803 hybrid_min_score = 0.03; hybrid_retriever.py:268,292 add 1/(rrf_k + rank) with rrf_k = 60. Computed by me: the maximum score for a document found in ONE leg is 1/61 = 0.01639, below the floor. Both legs must hit AND both be within rank 6 (2/66 = 0.0303 passes, 2/67 fails).
Impact
A question with no lexical overlap — "how do we decide when a subscription lapses?" — retrieves nothing even when the embedding leg ranked twenty near-perfect chunks. The dense leg exists for exactly those questions and is unreachable. Compounding it: the BM25 corpus is built only from LLM-generated markdown while symbol bodies are written only to the vector store, so code chunks can never be in both legs — the code_symbol_embed stage that costs ~2 300 s of every rebuild produces data that is mathematically unretrievable.
Fix
Set hybrid_min_score below 1/(rrf_k+1) — or to 0.0 — and rewrite the two tests that pin 0.03 against a rank-30 argument. Then feed symbol chunks into the BM25 corpus. Measure context_recall@10 before and after.

Архитектура

degrading, and one part is already the bottleneck

Граф импортов почти ацикличен — один рантайм-цикл и лишь 5 из 872 функциональных импортов замкнули бы цикл при подъёме. Значит структура ничего не заставляет: слои ещё разделимы. Отказывают не связи, а правила: в core/ и services/ ровно по 65 модулей со статистически неотличимым распределением входящих связей, поэтому нельзя написать тест, говорящий, куда класть новый файл. Этот вакуум и позволил воркеру импортировать тела своих задач из api/routes/ восемью рёбрами, невидимыми ни одной проверке. Исключение — спинной хребет чата и выполнения запросов: он уже узкое место. И класс дефекта, задокументированный в этом репозитории четырежды, живёт прямо сейчас в контроле безопасности: «выполнить сохранённый запрос» существует в пяти экземплярах, и уровень read-only выводится четырьмя разными способами.

Корректность кода

moderate-to-high, but concentrated

Дисциплинированный код с необычно честным отношением к своим провалам: 11 из 11 условных UPDATE проверяют rowcount, 10 из 10 get-or-create прикрыты настоящим уникальным индексом, 27 из 28 фоновых задач держат сильную ссылку, 287 кандидатов на пропущенный await оказались ложными. Не чиста ровно та категория, против которой репозиторий уже принял закон — тихая деградация: ratchet считает только ast.Constant, поэтому 15 обработчиков, возвращающих [] без записи в лог, стоят на один тип AST-узла дальше теста, написанного чтобы их ловить. Одиннадцать из двадцати четырёх находок — правка в одну-две строки, причём верный образец лежит в трёх файлах рядом.
