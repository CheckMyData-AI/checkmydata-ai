# Подключение второго проекта — инструкция и результат проверки

Составлено 2026-09-07. Каждое утверждение ниже подкреплено ссылкой `file:line`
или прогоном против реального приложения. Язык русский намеренно: это
операторский раннбук, а не документация репозитория (остальные файлы в `docs/`
— английские).

## Метод проверки

Три уровня, а не чтение кода на глаз:

1. **Код** — модели, роуты, конвейер индексации, фронтенд (`file:line` ниже).
2. **Отсутствие как измерение** — `grep` по `frontend/src/` на предмет обращений
   к API мультирепозиториев: ноль совпадений.
3. **Чёрный ящик** — временная проба против реального ASGI-приложения через
   тестовые фикстуры (`tests/integration/conftest.py:119`), 3 проверки, все
   зелёные, файл удалён после прогона. Вывод прогона приведён дословно.

## Короткий ответ

| Вопрос | Ответ | Доказательство |
|---|---|---|
| Интерфейс позволяет добавить второй проект? | **Да** | `Sidebar.tsx:520` кнопка «New project»; проба: два проекта создались, `GET /api/projects` → 2 |

## Главное ограничение: один проект = один репозиторий

Схема данных обещает мультирепозиторий, а продукт его не исполняет.

Таблица `project_repositories` существует, её докстринг прямо говорит
«supports multiple Git repositories per project» (`app/models/repository.py:1`),
и под неё есть полный CRUD — `POST/GET/PATCH/DELETE`
(`app/api/routes/repos.py:853`, `:896`, `:929`, `:958`).

Но **ничто из этой таблицы не читает**. Индексация и агент работают с
единственным полем `Project.repo_url` (`app/models/project.py:31`):

- клонирование репозитория — `app/knowledge/pipeline_runner.py:285-289`
  (`repo_url=project.repo_url`);
- запуск индексации — `app/api/routes/repos.py:160-163`: нет `repo_url` → `400`;
- GitAgent (живой git: коммиты, blame, diff) — `app/agents/git_agent.py:211-225`;
- ночная синхронизация — `app/services/daily_knowledge_sync_service.py:91`, `:182`.

Во всём `app/` таблицу трогают только три места, и ни одно не индексирует:
`ops/bm25_local_reconcile.py:81` (читает `last_indexed_commit`),
`services/ssh_key_service.py:153` (проверка ссылок на SSH-ключ перед удалением),
`services/repository_service.py` (сам CRUD).

**Проба, доказывающая это чёрным ящиком.** Проект без `repo_url`, но со строкой
в `project_repositories`:

```
PROBE POST /repositories              -> 201
PROBE GET  /repositories              -> 1 row(s): ['git@github.com:t/second.git']
PROBE POST /repos/{pid}/index         -> 400: {'detail': 'Project has no repository URL configured'}
```

Репозиторий добавлен, виден в списке — и индексатор его не видит.

**В интерфейсе этого API нет вообще.** `grep` по `frontend/src/` на
`repositories` даёт два совпадения, оба — маркетинговый текст
(`about/page.tsx:104`, `terms/page.tsx:71`). Клиент `frontend/src/lib/api/workspace.ts`
содержит `checkAccess`, `index`, `docs`, `doc`, `status`, `checkUpdates` — и не содержит CRUD
репозиториев. То есть добавить вторую строку можно только руками через API, и
пользы это не даст.

**Почему дефект не поймал CI.** Тесты `tests/integration/test_repo_operations.py:43-102`
проверяют только CRUD строки: создалась, прочиталась, переименовалась, удалилась.
Ни один не утверждает, что второй репозиторий проиндексирован. Ровно тот же
рисунок, что описан в `CLAUDE.md` про retrieval-эвалы: тест проверяет соседа, а
не продукт.

## Инструкция: подключить второй проект

### Шаг 0. Проверить, что тариф это позволяет

Лимит проектов — на владельца, не на воркспейс
(`app/services/entitlement_service.py:216-232`):

| Тариф | Проектов | Подключений | Источник |
|---|---|---|---|
| `base` $199 | **1** | 5 | `plan_catalogue.py:76` |
| `scale` $599 | 3 | 15 | `plan_catalogue.py:93` |
| `team` $900 | 10 | 50 | `plan_catalogue.py:111` |
| `enterprise` $1500 | без лимита | без лимита | `plan_catalogue.py:128` |

Что это значит на практике:

- **На `base` второй проект получит `402`** с предложением апгрейда. Nicegram с
  двумя базами в `base` укладывается (2 подключения из 5), а второй проект — нет.
- **Если биллинг выключен** (`billing_enabled=False`, как сейчас на проде —
  Stripe-ключи не заданы), лимитов нет вообще: `entitlement_service.py:95-96`
  возвращает `_no_plan()`, где `0` означает «без лимита», и проверка выходит на
  `if not ent.max_projects: return`. Это «деградация в открытую» и она намеренная.
- Лимит размера индекса (`max_index_bytes`, 1 ГБ на `base`) **не применяется
  нигде**: функция-счётчик `plan_catalogue.py:40` вызывается только из теста
  `test_four_tiers_priced_by_data_volume.py:217`, а `enforce_index_quota` не
  существует — в `entitlement_service.py` есть только `enforce_connection_quota`
  и `enforce_project_quota`. Второй проект по объёму индекса не заблокируют.

### Шаг 1. Права на создание проектов

Создание требует `User.can_create_projects` (`app/models/user.py:26`, по
умолчанию `False`) и подтверждённой почты. Отказы различаются намеренно
(`app/api/routes/projects.py:158-166`):

- почта не подтверждена → «Verify your email address to create projects»;
- права не выданы → «Your account is not permitted to create projects».

Владелец, у которого уже есть проект Nicegram, это условие проходит.

### Шаг 2. Создать проект

Интерфейс: сайдбар → секция **Projects** → **New project**
(`Sidebar.tsx:520` для десктопа, `:768` для мобильного). Форма в
`ProjectSelector.tsx:465-560`, отправка — `:301-316`.

Заполняется:

| Поле | Обязательно | Замечание |
|---|---|---|
| Name | да | уникально в пределах владельца — иначе `409` (`projects.py:191-195`) |
| Repository URL | нет | одно поле, один репозиторий |
| Branch | нет | по умолчанию `main`, валидируется как git-ref |
| SSH key | для `git@`/`ssh://` | ключи общие на владельца, не на проект |
| LLM-модели | нет | пусто = глобальные настройки |

Проверка доступа к репозиторию идёт до создания: форма дебаунсом дёргает
`POST /api/repos/check-access` (`ProjectSelector.tsx:210-232`), так что
неверный ключ видно сразу.

**SSH-ключи переиспользуются.** `GET /api/ssh-keys` не принимает `project_id` —
список owner-scoped, поэтому ключ, добавленный для Nicegram, доступен в форме
второго проекта без повторной загрузки.

### Шаг 3. Подключить базы

Проект → **Connections** → **New connection**. Подключения строго
проектные (`connection_service.py:374-386` фильтрует по `project_id`), проба
подтвердила: 1 в A, 0 в B.

Для баз за джамп-хостом (случай Nicegram) в форме есть SSH-туннель:
`ssh_host`, `ssh_user`, `ssh_key_id` (`ConnectionSelector.tsx:1279`,
валидация `:543` — при заданном `ssh_host` обязательны пользователь и ключ).

Тип базы в API — `postgres`, не `postgresql` (`connections.py:362`); в
интерфейсе это выпадающий список, так что промахнуться нельзя.

### Шаг 4. Проиндексировать

Порядок важен: **репозиторий индексируется только у проекта, у которого есть
хотя бы одно активное подключение** (`daily_knowledge_sync_service.py:96-98`).
Проект с репозиторием и без баз в ночную волну не попадёт.

Вручную: **Re-index repository** в проекте (`POST /api/repos/{id}/index`).
Первый прогон — полный: на репозитории в ~10 000 файлов это **3.3–3.4 часа**
(измерено дважды: 12 039 с и 12 329 с, см. `CLAUDE.md`).

### Шаг 5. Обязательно — развести часы ночной синхронизации

Это не косметика, а защита от падения воркера.

Волна ставит по одной задаче на каждый подходящий проект
(`app/main.py:903-906`), а ARQ-воркер держит `max_jobs = 8`
(`app/worker.py:422`). Часы по умолчанию у всех проектов одинаковые, значит
**два проекта = два полных индексирования одновременно в одном процессе**.

Почему это опасно именно здесь: один прогон измеренно упирается в **415 МиБ**
пикового потребления при `EMBEDDING_UPSERT_BATCH_SIZE=8` против квоты дино
**512 МиБ** (`CLAUDE.md`, раздел про память воркера). Два прогона в эту квоту не
влезают, а история R15/SIGKILL на `code_symbol_embed` в этом проекте уже была.

Развести можно, но **только через API — интерфейса для этого нет**. `grep` по
`frontend/src/` на `sync_schedule|sync-schedule|syncSchedule|sync-now` даёт ноль
совпадений, при живом бэкенде `app/api/routes/projects.py:557-576`:

```bash
# второй проект синхронизируется в 5 утра вместо 3
curl -X PUT "$BASE/api/projects/$PROJECT_ID/sync-schedule" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"enabled": true, "hour": 5}'

# проверить, что применилось (вернёт и next_run)
curl "$BASE/api/projects/$PROJECT_ID/sync-schedule" -H "Authorization: Bearer $TOKEN"
```

## Два репозитория — как делать сейчас

Рабочий способ ровно один: **два проекта, по репозиторию в каждом**.

| Хочется | Что делать |
|---|---|
| Два репозитория, общие базы | Два проекта; подключения продублировать в каждом (они проектные) |
| Два репозитория, разные базы | Два проекта — прямой путь, ничего обходить не нужно |
| Два репозитория, один чат//контекст | **Сейчас невозможно.** Знание разделено по проектам: коллекция вектора `project_{id}`, BM25-снапшот `{project_id}.json.gz`, `KnowledgeDoc.project_id` |

Цена решения «два проекта»: удваиваются подключения (лимит на владельца — 5 на
`base`), контекст между репозиториями не пересекается, и появляется риск из
шага 5.

## Найденные дефекты

Диагностика, не исправление — ничего в коде не менял.

| # | Дефект | Где | Эффект |
|---|---|---|---|
| 1 | `project_repositories` — мёртвая таблица: CRUD есть, индексации нет | `repos.py:853` vs `pipeline_runner.py:285` | API обещает мультирепо и молча не работает |
| 2 | В интерфейсе нет управления часом синхронизации | `projects.py:557` есть, во фронтенде 0 ссылок | Единственная защита от двойного индекса недоступна из UI |
| 3 | Два проекта → два одновременных индекса на воркере в 512 МиБ | `worker.py:422`, `main.py:903` | Риск SIGKILL при добавлении второго проекта |
| 4 | `max_index_bytes` тарифицирован, но не применяется | `plan_catalogue.py:40` вызывается только из теста | Оплаченный лимит не работает в обе стороны |
| 5 | Тесты мультирепо проверяют CRUD, а не индексацию | `test_repo_operations.py:43-102` | Дефект №1 проходит CI зелёным |

Дефект №1 разрешается двумя способами, и это продуктовое решение: либо
довести мультирепозиторий до конца (конвейер, GitAgent, UI), либо убрать
таблицу и CRUD, оставив честное «один проект = один репозиторий». Сейчас
worst case из трёх: обещание в схеме, тишина в проде.
