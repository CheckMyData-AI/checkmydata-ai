# T10 · P0 — Сохранение графа глушит heartbeat и рвёт ночную индексацию

**Найдено 2026-09-08 при исполнении T01** — то есть попыткой закрыть двухдневный разрыв,
которая сама была сжата реапером. Это не регрессия и не следствие недавних правок: оно
объясняет 52 исторических реапа на `graph_build` (недели 08-03…08-24) и то, почему
`index_repo` по расписанию падал 54 раза из 66 за 30 дней.

Исключено измерением: рестарта воркера нет, `R14`/`R15` нет, память дино в норме,
Redis свободен (4 соединения из 18). `builder.build` уже обёрнут в `asyncio.to_thread`
(`pipeline_runner.py:1742`), то есть CPU не держит event loop.

Молчание начинается ровно на переходе от построения графа к его **сохранению**
(`CodeGraphService.save_incremental`, вызывается из `_run_graph_build`,
`pipeline_runner.py:1710-1746`).

## Гипотеза (изменена 2026-09-08 — см. «Что показало измерение» ниже)

`save_incremental` документирован так: «load the existing graph, drop every symbol/edge
belonging to an `affected_files` path, splice in `new_graph`, and persist the union».
Существующий граф — **25 695 символов и 68 263 ребра**. То есть инкремент, добавивший
408 символов и 516 рёбер, переписывает ~94 000 строк.

Отсюда два независимых следствия, и оба надо проверить отдельно:
1. **Долго** — >5 минут при дефолтном `stale_running_heartbeat_timeout_seconds = 300`.
2. **Тихо** — за эти 5 минут не записан ни один heartbeat. Даже если сделать сохранение
   быстрым, шаг без биения останется бомбой замедленного действия при росте графа.

Второе важнее первого: писатель бита (`RunCoordinator.step`, N1 от 25.08) использует
**свою** сессию именно чтобы не стоять в очереди за рабочей — значит либо он не
запускается на время шага, либо контендит на пуле/пуллере (Supavisor session mode).

## Что показало измерение (T10.0, закрыто 2026-09-08)

**Гипотеза была верна наполовину, и глушила сердце не та половина.** Объём перезаписи
реален — но до записи ран не доходил вовсе. Хронология прода (все метки из логов):

```
20:49:26  graph_build: started (Building code graph from 82 parsed files)
20:49:27  code_graph: built 408 symbols, 516 edges
          ...14 минут 30 секунд полной тишины...
20:55:09  Reaper: reset stale runs — repo=1 runs=2 (timeout=300s)
21:03:57  graph_build: re-parsing 231 reverse-dependent file(s)   <- ЖИВ
21:03:59  code_graph: built 1378 symbols, 2299 edges
```

Между двумя этими строками `pipeline_runner.py:1758-1761` делает ровно две вещи:
`CodeGraphService.load_graph`, и `CodeGraphBuilder.reverse_dependents` по её результату.
Вторая на продовом графе меряется **0.009 с**. Значит всё время — в первой, а внутри неё
в конструкторе `CodeGraph`.

Причина — одно выражение, `code_graph.py:158`:

```python
key=f"{e.edge_type}:{len(self._graph.edges)}",
```

`G.edges` — вьюха, и `len()` по ней обходит всю структуру смежности, O(V+E). Вызов на
каждое ребро делает построение O(E×(V+E)). Замерено на продовой форме (25 695 символов,
68 263 ребра): **209.6 с на ноутбуке 2026 года**, ядро Standard-дино кратно медленнее —
отсюда наблюдаемые ~14 минут. Всё это синхронный Python без единого `await`, поэтому
корутина биения физически не может быть запланирована.

**Следствие для T10.1: биение, которое некому запланировать, стоит ровно столько же,
сколько его отсутствие.** T10.1 (#315) дал рану сердце на той строке, которую читает
реап, и это было необходимо — но недостаточно, и один только он ран бы не спас.

Значение ключа не читает никто: он существует лишь чтобы развести параллельные рёбра в
`MultiDiGraph`. Позиция в списке уникальна по построению и стоит ноль → **0.10 с**.

## Подзадачи

### T10.0 — Доказать механизм (обязательно первым) — **done**
1. Прочитать `CodeGraphService.save_incremental` / `save`: сколько строк читает и пишет,
   одной ли транзакцией, есть ли `await` внутри циклов записи.
2. Замерить локально на графе сопоставимого размера (сгенерировать 25k символов /
   68k рёбер): сколько занимает `save_incremental` с дельтой в 400 символов.
3. Ответить, **почему не бьётся сердце**: логировать факт биения (`DEBUG` → `INFO` на
   время диагностики) и увидеть, прекращается ли оно вообще или записи не доходят.
   `rowcount == 0` уже логируется — проверить, не он ли.
4. Вывод — в докстринг теста-репродукции. Не чинить недоказанное.

### T10.1 — Сердце должно биться во время долгой записи — **done (#315)**
Каким бы быстрым ни стало сохранение, шаг обязан биться. Варианты по итогам T10.0:
- вынести запись в `asyncio.to_thread` с отдельной синхронной сессией, оставив loop
  свободным для бита; **или**
- бить из отдельной задачи, запущенной на время шага, с гарантированно своим
  соединением, и проверить, что она не делит пул с записью.

### T10.2 — Инкремент не должен переписывать весь граф — **done**

> Сделано, и это отдельный выигрыш, а не причина реапа: инкремент на один файл теперь
> пишет 1 строку вместо ~94 000. Семантика слияния сохранена целиком, включая R3-1
> (обрезка висячих рёбер, теперь множественным `DELETE` на стороне БД) и R3-2
> (членство в кластере переносится по uid для символов **внутри** изменённых файлов —
> первая версия дельты это теряла, и первая версия теста этого не поймала).
Если T10.0 подтвердит объём: писать только дельту — удалять рёбра/символы затронутых
файлов и вставлять новые, не трогая остальные 94k строк. Осторожно: `save_incremental`
существует именно потому, что наивное `save` рушило M5/M6 для неизменённых файлов —
менять надо объём записи, а не семантику слияния.

### T10.4 — Построение графа не должно быть квадратичным — **done**
`code_graph.py:158`: `len(self._graph.edges)` → позиция в списке. 209.6 с → 0.10 с на
продовой форме. Тест механический (считает вызовы `OutMultiEdgeView.__len__`), а не по
времени: первая версия теста мерила отношение времён и **прошла на дефекте** — предсказать
отношение можно только зная стоимость `len()` на конкретной форме, а она зависит от числа
различных пар (src, dst) в фикстуре. Счётчик вызовов такой модели не требует.

### T10.5 — Обрезка R3-1 должна спрашивать меньше, а не быстрее — **done**
Первая версия дельты писала 1 176 значений вместо 837 571 — и работала **1 195 с** против
0.06 с сейчас. Причина: коррелированный `NOT EXISTS` на каждый конец каждого ребра проекта.
Чинится не индексом, а вопросом: R3-1 требует, чтобы ребро не пережило символ, удалённый
**этим прогоном**, то есть `doomed_uids − uids дельты` — точечный `DELETE` по
`(project_id, dst_uid)`, пропорциональный изменению. Слияние в памяти задавало вопрос по
всему проекту только потому, что граф у него уже был на руках.

Побочно устранено расхождение двух путей записи, и в неожиданную сторону: `CodeGraph`
держит рёбра к неразрешённым UID **намеренно** (`code_graph.py:153`), `save` их пишет, а
старая обрезка на каждом инкременте их стирала. Полная и инкрементальная индексация давали
разный граф для одного репозитория, и терял именно инкремент.

### T10.3 — Тесты
- реп­родукция: шаг длиной > таймаута реапера не приводит к реапу (бит идёт);
- дельта: инкремент на 1 файл пишет O(файл), а не O(граф) — считать выполненные
  DML-операции;
- регрессия M5/M6: символы неизменённых файлов и рёбра к ним переживают инкремент
  (существующие тесты `save_incremental` — не ослаблять).

## Наблюдаемость
- `INFO "graph_persist: %d symbols, %d edges, delta=%d files, %.1fs"` в конце шага —
  сейчас о самой дорогой операции пайплайна в логе нет ни строки.
- Counter `graph_persist_seconds` (гистограмма или сумма+счёт) — чтобы рост был виден
  до следующего реапа, а не после.

## Обходной путь на время работ (не замена фиксу)
`heroku config:set STALE_RUNNING_HEARTBEAT_TIMEOUT_SECONDS=900` — реапер перестаёт
убивать живой прогон, ценой того, что настоящий труп лежит 15 минут вместо 5.
Требует записи в `DELIBERATE` map (`CONVENTIONS.md` §9). **Только с фиксацией в леджере
и снятием после T10.1** — иначе это тот самый молчаливый дрейф, который аудит и ловил.
